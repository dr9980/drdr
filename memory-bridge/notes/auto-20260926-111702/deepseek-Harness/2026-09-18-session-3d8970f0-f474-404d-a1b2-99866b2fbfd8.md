### 评估 @liustack/modsearch 插件并给出"不建议安装"的结论

**问**：这个插件（ModSearch）怎么样，我需要安装吗？

**做**：
- 实测确认当前环境**已有可用联网能力**：本会话 `web_search` 正常返回结果；配置为 `searchProvider: deepseek-official` + `fetchProvider: http`，由 `@deepseek-ai/dsh-web-search-deepseek`（用用户自己的 DEEPSEEK_API_KEY）和 `@deepseek-ai/dsh-web-fetch-http` 支撑。
- 解码插件的 `cordis.patch.yml`，确认其机制是**替换**而非新增：把 `web` 行的 `searchProvider` 从 `deepseek-official` 改为 `modsearch`，并 insert `@liustack/modsearch`。
- 读源码 `dsh/index.js`：插件只注册一个 search provider（id `modsearch`，`available: () => true`），`search()` 通过子进程调用自带 CLI（`dist/main.js -q <query> --source web --timeout 55000`）；**不注册 fetch provider**，`read_page` 是独立工具。
- 查 GitHub/npm 元数据：498 star、20 fork、MIT、作者 Leon Liu（liustack，即已装的 `modlens` 作者）、3 天前仍有提交、仓库 2 月建立；运行时依赖仅 `commander` + `undici`；`engines.node >=22.13`（本机 v24.21 ✓）。
- 实测三个默认后端在本机可达：firecrawl 200 / tavily 405 / exa 404（均为正常响应），排除国内网络问题。
- 核查 `fetchProvider` 被 patch 丢弃的影响：因 ModSearch 不注册 fetch provider，fetch 侧仍只有 `dsh-web-fetch-http` 一个，按选择规则（无 id 配置 + 唯一可用 provider → 自动选中）**不会坏**。

**结论/决定**：
- **不建议安装**（除非明确需要 X 搜索）。理由：DSH 的 web seam 是**单选**的，`searchProvider` 只能指一个 provider，装它是 A 换 B，不是"给模型加上联网"；用户现有官方通道已可用，且无 Firecrawl 那种每月 1,000 credits 的额度上限。
- 插件真正新增的只有两项官方没有的能力：`x_search`（搜 X，未装 Grok Build 时降级为普通网页搜索并标注 `degraded`）和 `read_page`（经模型加工的单页阅读：摘要+正文抽取+外链+不确定项+告警）。
- 给出三个方案：A 不装（推荐）；B 装但用用户层 `cordis.patch.yml` 把 `web` 行 `searchProvider` 钉回 `deepseek-official`，只取 `x_search`/`read_page`（作者注释确认可行："a later profile patch can pin any provider back"）；C 全量装（确实常搜 X 或官方搜索常被限流时）。

**要点**：
- 安全前提（作者源码注释原文）：`/modsearch/config` 路由**不继承 dsh Connection 鉴权，插件自身不施加任何 Host / Origin / Fetch Metadata 策略**。仅在**未配置任何 API Key** 时基本无害；一旦填入 Tavily/Exa/Firecrawl 密钥，恶意网页理论上可 POST 该路由篡改某引擎 `baseURL`，下次搜索时带走密钥。要装就保持免密钥状态。
- 免费额度限制：Firecrawl 免注册通道每月 1,000 credits。
- 源码质量正面信号：引擎名做规范化而非裸下标查找（防原型污染）、配置写入拒绝符号链接、0600 权限 + 原子改名、请求体 64KiB 上限、密钥不回传浏览器。
- 后续动作约定：装前先跑 `dsh-security-audit` 扫插件，装完**不重启**，并把结果与验证反馈给用户。
